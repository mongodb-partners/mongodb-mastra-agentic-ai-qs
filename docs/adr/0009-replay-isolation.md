# ADR 0009: Demo mode replays immutable `replay_*` collections

Status: accepted

## Context

Marshal is demonstrated in front of an audience. A demo that calls the LLM live is one API outage, one
rate limit, or one hotel network away from a blank screen, and the failure lands mid-sentence.

So there is a recorded run. The naive version of that is: record into the same collections the live
pipeline writes, and read them back in demo mode. It does not survive contact with a shared cluster.
One live run, or one live reset, overwrites or destroys the recording. Someone switching modes on the
same cluster loses the recording without noticing until the next demo.

## Decision

`pnpm bake` snapshots the four working recording collections into dedicated `replay_*` collections:

| Working (live writes, a reset clears) | Immutable replay copy |
|---|---|
| `agent_events` | `replay_events` |
| `case_analysis` | `replay_analysis` |
| `reviews` | `replay_reviews` |
| `audit_trail` | `replay_audit` |

Demo mode reads only the replay copies, through `recordingSource(demoMode)`. Live runs and resets never
touch them. The two modes coexist on one cluster indefinitely.

A fifth collection, `replay_meta`, carries the recording's provenance as a single document:
`corpus_size`, `decided_precedents`, `source_db`, `recorded_at`, plus `app_commit`, `atlas_tier`, and
`llm_model`.

## Consequences

### Provenance travels with the recording, and it has to

Demo mode publishes the recording's timings as latency figures in the status bar. Those are performance
claims, and a performance claim without provenance cannot be checked. `corpus_size` alone answers "at
what scale" and leaves "on what hardware, at what revision, with which model" unanswerable.

Each field is load-bearing for a specific reason. The tier matters because a second 1M-document vector
index on one M30 moved an untouched index's p50 from 21.0 to 179.6 ms; latency read off a recording says
nothing without the tier it was recorded on. The model matters because it is the dominant term in the
span, so a recording re-baked on a different model is a different measurement rather than a fresher one.
The commit matters because the artifact outlives the shell session that knows it. The measured cost of
omitting it: attributing one recording required reading `git reflog` on the machine and matching a
checkout timestamp against `recorded_at`. Recoverable that day, not recoverable after the machine is
replaced.

Every provenance field is a plain string, `'unknown'` when undeterminable, and never absent, on the way
in and on the way out. A reader must get something printable without a guard, because `'unknown'` is a
legible answer and `undefined` renders as a blank that reads as a value.

### The replay cluster does not need the corpus

The recording stores precedent content inline, so it renders without the source corpus. Loading a
million documents onto a box that only ever replays would cost disk and seeding time to answer one
count, and it would create a hazard that not loading them avoids.

Synthetic ids are positional. The same id means a different transaction in two corpora generated by
different revisions of the generator: `txn-syn-00016` is `structuring` and escalated in the 12k corpus,
and `clean_approve` and approved in the 1M one. A cluster holding look-alike documents would let the
dangling-id health check pass while every cited id pointed at something else. An empty cluster fails
that check honestly.

`readReplayMeta` returning `null` is a supported state, not an error. An artifact exported before
`replay_meta` existed restores without it and the caller falls back to the live count. A demo reporting
the replaying cluster's own size is understated, which is a much better failure than refusing to start.

### The audit key has to be normalized on export

The chain in the recording is signed with whatever `AUDIT_SECRET` was set when it was baked. Baking on a
deployed box therefore produced an artifact restorable only to that box. Export normalizes the signing
key so the artifact is portable, and `pnpm restore:replay` re-signs it for the target deployment.

The residual trap is worth stating: a deployment that restores and *then* sets a fresh `AUDIT_SECRET`
shows a broken chain, because the records were signed under a different key. That is reported as
`key_mismatch` rather than `hmac_mismatch` specifically so it can be told apart from tampering. See
[ADR 0005](0005-hmac-audit-chain.md).

### Recorded timings go stale

The replay paces itself off the recorded timestamp deltas, so a frozen recording plays back at the speed
of the machine and model that produced it. As the live path gets faster, the demo looks slower than the
product. The restore path retimes the artifact for this reason, and it is a maintenance obligation rather
than a solved problem: a recording is a measurement with a date on it.

### Tests must assert the contract, not the artifact

Re-baking the recording once broke three tests that asserted properties of the artifact rather than of
the code that reads it. A fixture test that pins incidental values turns every legitimate re-bake into a
test failure. Assert the shape and the invariants.
